# Deploying

Nothing changes. The résumé builder adds no API route, no database, no
environment variable and no server runtime — `/resources/resume-builder`
prerenders to static HTML like every other page, and the build output confirms
it:

```
Route (app)
├ ○ /resources
├ ○ /resources/resume-builder
○  (Static)  prerendered as static content
```

So the existing Vercel deployment picks it up with no configuration.

---

## Vercel

Push to the connected branch. If you are setting the project up from scratch:

1. Import the repository at [vercel.com/new](https://vercel.com/new).
2. Set **Root Directory** to `iem-website`.
3. Deploy. Vercel detects Next.js and needs nothing else.

Or from inside `iem-website/`:

```bash
vercel --prod
```

## What ships

About **4 MB** of new static assets, all under long cache headers
(`/fonts/:path*` and `/templates/:path*`, 180 days with a year of
stale-while-revalidate — see `next.config.ts`):

| | |
| --- | --- |
| `public/fonts/resume/*.ttf` | 2.4 MB, 30 Latin-subset faces |
| `public/templates/*/thumb.png` | 1.4 MB, eight picker previews |
| `public/templates/*/original.pdf` | ~1 MB, the verification references |

Only the faces a chosen template declares are fetched, so a student picking
Harvard downloads four files, not thirty.

The JavaScript for the builder is a lazy-loaded island: the other nine pages
carry none of it, and the three exporters load only when their button is first
pressed.

### Not shipped

`public/fonts/resume/_source/` (the full downloaded fonts) and `.verify/` are
gitignored. Both are regenerated by maintenance scripts, not by the build.

## Content Security Policy

**No changes needed.** The strict CSP in `next.config.ts` already allows
everything the builder does:

- `font-src 'self'` — fonts are same-origin under `/fonts/resume/`
- `connect-src 'self'` — the only fetches are those fonts
- the preview is inline SVG, not an embedded object
- downloads use `blob:` URLs from an `<a download>`, which CSP does not gate

Nothing is fetched from a CDN at runtime, which is why the fonts are vendored
rather than linked.

## Maintenance scripts

None of these run during a build. They are for maintainers, and they need Python
with `pymupdf pillow numpy fonttools brotli`.

```bash
npm run fonts:resume       # re-download and re-subset the fonts
npm run verify:templates   # regenerate the verification report
npm run resume:thumbs      # regenerate the picker thumbnails
npm test                   # the template × fixture matrix
```

`verify:templates` is the one to run after touching a template or the engine. It
writes `docs/resume-builder/verification_report.md`; commit the change so the
accuracy numbers stay under review.

### CI

A workflow that runs `npm ci && npm run lint && npm test && npm run build` is
enough for pull requests. Adding the verification pass needs Python and a
`pip install pymupdf pillow numpy` step; it is worth it if templates are being
edited often, and skippable if they are not.

The stronger check — compiling the emitted `.tex` with a real TeX Live and
diffing the result against our own PDF — needs a TeX container and several
minutes. It belongs on a nightly or manual workflow rather than on every push.

## Rollback

The builder is one route and one directory. Removing it means deleting
`src/app/resources/resume-builder/` and `src/resume/`, dropping the card from
`src/app/resources/page.tsx` and the route from `src/app/sitemap.ts`. Nothing
else in the site imports from it.
